## Debug Imports by Their Original Names

중단점에서 멈췄는데 import한 변수를 원래 작성한 이름으로 확인할 수 없나요? webpack은 import를 생성된 namespace 객체의 속성을 읽는 코드로 바꿀 수 있습니다. 소스 맵은 디버거가 원본 소스를 찾도록 도와주지만, 원래 이름의 값을 어떻게 평가해야 하는지는 알려주지 않습니다.

새로운 `-scopes` 접미사를 사용하면 소스 맵에 해당 정보를 추가할 수 있습니다.

```js
export default {
  mode: "development",
  devtool: "source-map-scopes",
};
```

예를 들어 소스 맵 스코프를 지원하는 디버거는 webpack이 기록한 생성 코드의 표현식을 이용해 import한 `formatPrice`를 찾을 수 있습니다. `eval-source-map-scopes`를 사용하거나 `SourceMapDevToolPlugin`을 직접 설정할 때 `scopes: true`를 지정할 수도 있습니다.

이 기능은 선택적으로 활성화하며, 출력되는 JavaScript는 변경하지 않고 소스 맵에 데이터만 추가합니다. 다만 이번 릴리스에서는 module concatenation으로 병합된 module의 import binding은 아직 포함되지 않습니다. 위 개발 설정에서는 기본적으로 concatenation이 비활성화됩니다.

## An Asset Manifest for Server Rendering

브라우저가 JavaScript를 로드하기 전에 서버에서 지연 로드되는 경로를 렌더링할 수 있습니다. 해당 경로의 스타일시트가 JavaScript와 함께 로드된다면 사용자는 처음에 스타일이 적용되지 않은 페이지를 보게 됩니다.

`SSRManifestPlugin`은 서버가 이런 에셋을 미리 로드하는 데 필요한 정보를 제공합니다. 클라이언트 빌드에 추가하세요.

```js
import webpack from "webpack";

export default {
  target: "web",
  output: {
    publicPath: "/assets/",
  },
  plugins: [new webpack.SSRManifestPlugin()],
};
```

이 plugin은 원본 module 경로와 클라이언트 에셋을 연결하는 `ssr-manifest.json`을 생성합니다. 공유 chunk와 module에 도달하는 데 필요한 비동기 상위 chunk가 포함되며, 스타일시트는 cascade 순서대로 나열됩니다.

서버 렌더링 통합 코드에서는 렌더링한 module을 조회하고 해당 경로를 사용해 스타일시트 링크와 ESM 출력용 module preload를 추가할 수 있습니다. plugin은 매니페스트만 제공하므로 렌더링한 module을 추적하고 태그를 작성하는 작업은 통합 코드에서 처리해야 합니다. `output.publicPath`에는 클라이언트 에셋을 제공하는 URL 접두사를 설정하세요. `"auto"`로 설정하면 경고를 출력하고 대신 `/`를 기본 경로로 사용합니다.

네이티브 CSS의 서버 렌더링도 수정되었습니다. 별도의 `target: "node"` 빌드에서 `__webpack_css_server_styles__`를 통해 스타일을 수집할 수 있습니다. 이 API는 5.110에서 도입되었고, 이번 릴리스부터 document가 없는 target에서도 수집이 동작합니다.

## Export More Than the Last Entry Module

entry 배열은 나열한 모든 module을 실행하지만, 일반적으로 라이브러리는 마지막 module의 export만 노출합니다. 공개 API의 각 부분을 별도 module에서 관리한다면, 이를 다시 export하기 위한 entry 파일을 추가로 작성해야 할 수 있습니다.

`library.entryExports: "all"`을 설정하면 각 module의 export를 하나의 라이브러리로 모을 수 있습니다.

```js
export default {
  entry: ["./src/format.js", "./src/validate.js"],
  output: {
    filename: "utils.mjs",
    library: {
      type: "module",
      entryExports: "all",
    },
  },
};
```

두 파일이 각각 `formatPrice`와 `validateOrder`를 export한다면, 사용자는 `utils.mjs`에서 둘 다 import할 수 있습니다. `output.library` 또는 개별 entry의 `library` 옵션에서 설정할 수 있습니다.

기본값은 여전히 `"last"`입니다. `"all"`에서 이름이 충돌하면 `export *`와 비슷하게 처리합니다. 두 module이 서로 다른 binding을 같은 이름으로 export하면 webpack은 해당 이름을 제외하고 경고를 출력합니다. 두 module에서 동일한 binding을 다시 export하는 것은 괜찮습니다.

## Choose Which Dependencies to Share

Module Federation으로 의존성을 공유한다고 해서 설치된 모든 버전을 공유해야 하는 것은 아닙니다. 앱에서 한 메이저 버전을 사용하는 동안 하위 의존성에는 다른 버전이 필요할 수 있습니다.

새로운 `include`와 `exclude` 필터를 사용하면 공유할 module을 선택할 수 있습니다. 예를 들어 `^8.3.2`에 맞는 `uuid` 버전만 공유하고, 하위 의존성이 사용하는 이전 버전은 일반적인 방식으로 resolve할 수 있습니다.

```js
import webpack from "webpack";

export default {
  plugins: [
    new webpack.container.ModuleFederationPlugin({
      name: "shop",
      shared: {
        uuid: {
          requiredVersion: "^8.3.2",
          include: { version: "^8.3.2" },
        },
      },
    }),
  ],
};
```

필터에 포함되지 않은 module은 일반 의존성처럼 resolve되어 bundle에 포함됩니다. 소비하는 module의 버전 필터는 로컬 fallback을 검사하므로, `import: false`로 fallback을 제거하면 적용되지 않습니다.

요청을 기준으로 필터링할 수도 있습니다. `lodash/`처럼 `/`로 끝나는 공유 키에서는 `include.request`나 `exclude.request`가 요청의 나머지 부분과 일치하는지 검사합니다. 예를 들어 `lodash/get`에서는 `get`을 검사합니다.

## Name the Chunks in Your HTML

[네이티브 HTML 지원](/guides/native-html/)을 사용하면 webpack이 페이지에 필요한 script와 style을 추출합니다. 이제 HTML에서 해당 chunk의 역할을 나타내는 이름을 직접 지정할 수 있습니다.

```html
<!-- webpackChunkName: "checkout" -->
<script type="module" src="./checkout.js"></script>
```

페이지 전반에 적용할 이름 규칙은 `module.parser.html.chunkName`으로 설정하세요. 함수 또는 `[page]`, `[name]`, `[index]`, `[type]`을 사용하는 템플릿을 지정할 수 있습니다.

```js
export default {
  entry: "./src/index.html",
  experiments: {
    html: true,
  },
  module: {
    parser: {
      html: {
        chunkName: "[page]-[type]-[index]",
      },
    },
  },
};
```

`webpackChunkName` 주석은 이 규칙보다 우선합니다. 이름을 지정한 인라인 script는 새로운 실행 묶음을 시작하며, 뒤따르는 호환 가능한 script와 chunk를 공유할 수 있습니다. 한 HTML 문서에서 서로 다른 태그가 같은 chunk 이름을 요청하면 webpack은 chunk를 분리하기 위해 각각 다른 이름을 부여합니다.

webpack은 호환 가능한 인라인 script 실행 묶음도 공유 chunk로 합칩니다. 실행 순서를 유지하면서 작은 script마다 별도의 chunk가 생기는 것을 방지합니다. 비동기 script, 외부 script 등 실행 순서에 영향을 주는 경계에서는 묶음을 분리합니다. 조건에 맞는 chunk를 페이지에 다시 인라인으로 작성하려면 `output.html.inline`이나 `webpackInline` 주석을 사용하세요.

## Async Values in DefinePlugin

소스 코드의 상수를 치환하기 전에 파일을 비동기로 읽어야 하나요? 이제 `DefinePlugin.runtimeValue`는 해당 값을 사용하는 module을 webpack이 파싱하기 전에 비동기 callback을 기다릴 수 있습니다.

```js
import { readFile } from "node:fs/promises";
import { fileURLToPath } from "node:url";
import webpack from "webpack";

const versionFile = fileURLToPath(new URL("./version.txt", import.meta.url));

export default {
  plugins: [
    new webpack.DefinePlugin({
      APP_VERSION: webpack.DefinePlugin.runtimeValue(
        async () =>
          JSON.stringify((await readFile(versionFile, "utf8")).trim()),
        [versionFile],
      ),
    }),
  ],
};
```

파일을 의존성으로 지정하면 파일이 변경될 때 webpack이 값을 다시 계산합니다. `JSON.stringify`는 결과를 JavaScript 문자열 리터럴로 만들어 앱의 `APP_VERSION`을 치환할 수 있게 합니다.

`async` 함수는 자동으로 인식됩니다. callback을 `async`로 선언하지 않았지만 promise를 반환한다면 runtime value 옵션에 `{ async: true }`를 전달하세요. 이 작업은 컴파일 중에 처리되므로 앱에서 비동기 조회가 추가로 발생하지 않습니다.

## Find More Shared Chunks

한 module 그룹은 페이지 A, B, C에서 사용하고 다른 그룹은 A, B, D에서 사용한다고 가정해 보세요. 두 그룹 모두 A와 B에 필요하지만, 기존 webpack의 chunk 조합에서는 A와 B가 공유하는 부분을 놓칠 수 있습니다.

새로운 `optimization.splitChunks.dedupDepth` 옵션은 이렇게 겹치는 부분을 탐색합니다.

```js
export default {
  optimization: {
    splitChunks: {
      chunks: "all",
      dedupDepth: 1,
    },
  },
};
```

값이 `1`이면 한 차례 탐색하고, 더 높은 값을 지정하면 이전 차례에서 찾은 조합까지 탐색합니다. 발견된 후보에도 cache group 규칙이 적용됩니다. 자동 이름 지정을 유지하고 `minSize` 또는 `minSizeReduction`으로 최소 크기나 크기 감소 조건을 지정한 그룹에서 이 후보를 사용합니다. 기본 cache group은 해당되지만, 이름 지정 함수를 포함해 사용자 정의 `name`을 설정한 그룹은 해당되지 않습니다.

기본값은 `0`이며 `experiments.futureDefaults`를 사용하면 `1`입니다. 먼저 한 차례만 탐색하고 빌드 결과와 소요 시간을 비교한 뒤 값을 늘리세요.

## More Control over CSS and JSON Assets

복사한 스타일시트는 webpack의 CSS parser를 거치지 않고 출력될 수 있습니다. 새로운 minimizer 옵션인 `customMedia`와 `customSelectors`를 사용하면 대신 압축 과정에서 해당 사용자 정의 규칙을 해석할 수 있습니다.

```js
export default {
  mode: "production",
  output: {
    copy: "public",
  },
  optimization: {
    minimize: {
      css: {
        customMedia: true,
        customSelectors: true,
      },
    },
  },
};
```

이 옵션은 기본적으로 비활성화되어 있습니다. webpack의 네이티브 CSS parser가 처리하는 스타일시트는 이미 해당 단계에서 custom media와 selector를 해석합니다. 새 설정은 그 단계를 거치지 않는 에셋을 위한 것입니다. custom selector를 확장할 때는 target의 `:is()` 지원 여부도 고려합니다.

CSS 압축 시 브라우저 호환성도 더 신중하게 다룹니다. target에 브라우저를 지정하지 않으면 webpack은 Browserslist의 `defaults` 쿼리를 사용합니다. 브라우저 목록에 webpack의 호환성 데이터에 없는 엔진이 포함되어 있다면, 최신 CSS를 지원한다고 가정하는 변환을 피하고 vendor prefix가 붙은 표기를 유지합니다.

더 적극적으로 변환하는 두 가지 CSS 옵션도 있습니다. 브라우저를 명시적으로 선택하지 않은 경우 `dropOverriddenDeclarations`는 기본 쿼리를 사용하지 않고 뒤의 값으로 덮어쓴 선언을 제거할 수 있게 합니다. `convertApproximateColors`는 색상을 근사한 16진수 값으로 바꿀 수 있습니다. 호환성이나 표시되는 색상이 달라질 수 있으므로 둘 다 기본적으로 비활성화되어 있습니다.

출력되는 JSON 에셋과 웹 매니페스트도 기본 minimizer로 압축할 수 있습니다.

```js
export default {
  mode: "production",
  optimization: {
    minimizeOptions: {
      json: true,
    },
  },
};
```

`.json`, `.webmanifest` 같은 출력 파일에서 불필요한 공백을 제거합니다. `experiments.futureDefaults`를 사용하면 기본적으로 활성화되고, 그렇지 않으면 위와 같이 직접 설정해야 합니다. 해당 에셋을 처리하는 사용자 정의 minimizer를 설정했다면 webpack은 그 minimizer에 작업을 맡깁니다.

## Plugins for Multiple Configurations

설정 배열로 클라이언트와 서버 bundle을 빌드하고 있나요? 이제 배열 자체에 `plugins`를 추가할 수 있습니다. webpack은 각 plugin을 `MultiCompiler`에 한 번씩 적용하여 전체 빌드에 접근할 수 있게 합니다.

예를 들어 두 설정에 하나의 진행 상황 plugin을 적용할 수 있습니다.

```js
import webpack from "webpack";

export default Object.assign(
  [
    {
      name: "client",
      target: "web",
      entry: "./src/client.js",
      output: { filename: "client.js" },
    },
    {
      name: "server",
      target: "node",
      entry: "./src/server.js",
      output: { filename: "server.js" },
    },
  ],
  { plugins: [new webpack.ProgressPlugin()] },
);
```

개별 설정에 추가한 plugin은 계속 해당 설정의 compiler에 적용됩니다. `ProgressPlugin`처럼 `MultiCompiler`를 지원하는 plugin을 여러 빌드에 걸쳐 사용하려면 배열의 `plugins` 속성을 사용하세요.

## Smaller Changes Worth a Look

- **더 많은 위치에서 glob 필터 지원.** `snapshot.managedPaths`, `immutablePaths`, `unmanagedPaths`는 `**/node_modules`처럼 프로젝트 context를 기준으로 하는 glob을 받습니다. `output.clean.keep`, `experiments.lazyCompilation.test`, split chunks cache group의 `test` 등 다른 필터에서도 `{ glob: "..." }` 조건을 사용할 수 있습니다. 예를 들어 `test: { glob: "**/vendor/**" }`는 `vendor` 디렉터리 아래의 module과 일치합니다.
- **Plugin 작성자를 위한 공개 API 확대.** 더 많은 내장 plugin을 해당 namespace에서 사용할 수 있으며 `webpack.template.DependencyTemplate`, `webpack.module.NullFactory`, `webpack.util.makeSerializable`도 제공됩니다. 이전 export 위치 중 일부는 deprecated 상태입니다.
- **ESM 내부 요소에 ESM 이름 사용.** `Harmony*` 이름은 `ESM*` 이름으로 대체되어 deprecated 상태입니다. 예를 들어 `webpack.dependencies.HarmonyImportDependency` 대신 `webpack.dependencies.ESMImportDependency`를 사용하세요.

소스 맵이 없는 module에서는 빌드 해시를 계산한 뒤 불필요한 소스 버퍼를 해제합니다. eval 소스를 감싼 뒤에는 캐시된 eval 소스를 지우고, chunk를 출력한 뒤에는 렌더링된 module 소스도 해제합니다.

## Bug Fixes

변경 사항이 재빌드 결과에 제대로 반영되도록 여러 문제를 수정했습니다. 캐시된 빌드 간에 loader resolve 의존성을 유지하고, module 연결이나 비동기 상태가 바뀌면 캐시 결과를 무효화하며, 누락되었던 module이 다시 나타나면 re-export와 경고를 갱신합니다.

이제 watch mode는 빌드 중 삭제된 파일을 감지하고 재빌드를 예약합니다. 사용하지 않는 의존성 하나가 사라지고 다른 의존성이 다시 나타나는 경우에도 생성된 코드를 갱신합니다. 이전 빌드의 stats를 보관하는 도구는 이후 빌드에서 stats에 기록된 module이 제거되어도 해당 stats를 읽을 수 있습니다.

Hot update는 새로 추가된 deferred import도 처리하고, 공유 runtime에서 비동기 스타일시트가 올바르게 로드되며, `output.clean`은 최신 hot update 파일을 유지합니다.

전체 변경 사항과 기여자 목록은 [5.112.0 릴리스 노트](https://github.com/webpack/webpack/releases/tag/v5.112.0)를 참고하세요.
